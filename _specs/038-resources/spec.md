# Starting blank: what each agent loads

## Outcome

Every agent hobkin starts on Pi begins with hobkin's own instructions and tools, the few packages hobkin starts its kind with, and nothing else of Pi's until the user chooses it, and never Pi's own AGENTS.md. Background starts with MCP, pi-agentic-search and pi-search-hub; Work and durable hobkins with pi-agentic-search and pi-search-hub; the main chat with nothing of Pi's. hobkin's own include its development texts (`045-dev-system`) and, for a run that works in a project, the project's own AGENTS.md or CLAUDE.md, beneath hobkin's text. On Settings › Skills and Settings › Pi extensions the user sees what Pi has installed (packages such as pi-agentic-search and the web search ones, extensions and skills of their own) beside hobkin's own instructions, and chooses what each kind of agent loads: the main chat, background jobs and routines, Work runs, and durable hobkins. Every run is held to that choice. Settings also shows what each kind actually loaded and when each resource was last used. Runs move to this only when the user turns it on, and one Action Item then lists what each kind loaded before and loads now.

## Decisions

### What a resource is

- A resource is something of Pi's that changes what an agent knows or can do. Three types are offered.
  - A package: a Pi package installed at user level, as Pi's settings list it under `packages`. It is chosen whole, with the extensions and skills it holds. Its id is `package:` and Pi's own source for it, such as `package:npm:@siddr/pi-web-search` or `package:../../Poetry/pi-agentic-search`.
  - An extension or a skill of its own, outside any package, as Pi resolves it at user level: Pi's `extensions/` and `skills/` folders and its `extensions` and `skills` settings. Its id is `extension:` or `skill:` and its path inside Pi's folder, or its absolute path when it is outside.
  - A built-in: `builtin:mcp`, which brings the MCP servers Integrations has on (`023-integrations`), and `builtin:llama.cpp`.
  - ~~A context file: `context:pi` is the AGENTS.md (or CLAUDE.md, or AGENTS.override.md) in Pi's folder. `context:folder` is the AGENTS.md and CLAUDE.md files Pi finds in the folder a run works in and the folders above it.~~ Replaced by the user on 2026-11-14: context files are no longer chosen. Pi's AGENTS.md loads in no run, and the project's own files are hobkin's own (see "Context files" below).
- Prompt templates and themes are never loaded and not offered. They serve Pi's terminal, and no hobkin run uses them.
- Pi itself is not a resource. Its built-in tools, its base prompt, and its code mode and tool search load in every run that uses tools, as they do in the main chat today (`src/cli/pi-extensions.mjs:41`).
- hobkin's own instructions are not chosen. They always load, and Settings lists them. This keeps the decision already taken: blank means no inherited Pi resources, not the loss of the user's directions, hobkin's memory or its bridge tools (`work-in-progress.md:388`). From 2026-11-14 they also hold hobkin's own AGENTS.md and skills, which `045-dev-system` decides, and, for a run in a project, the project's own files.
- Today `resource-policy.mjs` names six types and ten purposes, and its ids cannot hold `@` or `/` (`src/cli/resource-policy.mjs:3-7`). It becomes the three types and four kinds here. An id may hold any printable characters, up to 300.

### Context files

- The user, 2026-11-14: "i want the global to stay, hobkin should overwrite that and introduce our own agents.md". The AGENTS.md (or CLAUDE.md, or AGENTS.override.md) in Pi's folder is the user's, for their own Pi. It is not offered, and no run hobkin starts loads it, on Pi or on Claude Code. hobkin's own AGENTS.md takes its place (`045-dev-system`).
- The user, the same day: "it can use the project, but hobkin will go on top". A Background, Work or durable run that works in a folder reads that folder's own files: the AGENTS.md or CLAUDE.md that Pi would find there and in the folders above it, one file per folder by Pi's order (`loadContextFileFromDir`, Pi's `dist/core/resource-loader.js:129-148`), leaving out Pi's folder and hobkin's home. This answers the open question about Work and a project's own files: they load from the start, with no switch.
- They come after hobkin's own text, under one line hobkin adds: these are the project's own instructions, and where they disagree with the user's directions or hobkin's AGENTS.md above, those win. Each run passes `--no-context-files`, so Pi finds none of them by itself, and the run's wrapper appends them with `--append-system-prompt` after hobkin's own. Pi puts appended text in that order (`dist/core/system-prompt.js:96-99`).
- The main chat and hobkin's fixed runs read no project file. A helper reads only what its parent passes it: a Work do run's helper gets its parent's project files (`045-dev-system`), which is hobkin's own, not Pi's discovery.
- `context:folder` already finds these files with Pi's own `loadProjectContextFiles` and leaves out Pi's folder and hobkin's home (`src/cli/resource-catalog.mjs:189-193`). That code stays as the finder, and it stops being an item of the catalog.

### Where the list comes from, and why it is trusted

- The catalog is built by hobkin's runtime with Pi's own code: `DefaultPackageManager.resolve` with missing packages skipped, as `extensionPaths` does today, so nothing is installed or run to find out (`src/cli/pi-extensions.mjs:20-28`). Only what Pi marks as user scope and on is kept. Something the user switched off in Pi is not offered.
- Nothing from a folder's `.pi` is listed or loaded: not its settings, extensions, skills or MCP servers. Today a project's own extensions load into the routines that run in it (`test/cli-pi-extensions.test.mjs:52`), and every run with tools outside Work passes `--approve` (`src/cli/harnesses.mjs:74`). Both end. Every run passes `--no-approve`.
- A selection holds ids, never paths. When a run starts, hobkin builds the catalog again and loads the paths it finds now for the chosen ids, each an existing file or folder. A path in a selection, in a run request or in any file is refused. So a path the user did not choose is never loaded because a file named it.
- A skill's name and line come from its SKILL.md frontmatter, and a package's from its package.json, read through Pi's loaders. An extension's tools are not known until a run loads it. Settings shows them from the last run that did.
- hobkin's own exclusions stay. pi-emote is never offered, since hobkin has its own face. pi-auto-review is never offered either: the user, 2026-11-14, "we are not using pi-auto-review". hobkin's own review is Change Review (`032-change-review`), and every place that read pi-auto-review reads Change Review instead (`045-dev-system`, "Change Review in place of pi-auto-review"). pi-cache-compact-preserved-messages, pi-memory and pi-scheduler are not offered to the main chat, for the reasons in `src/cli/pi-extensions.mjs:9-16`. The other kinds may choose them.
- A live host reads Pi's own folder. A host started in development or a test reads its own Pi folder, by the rule Integrations uses (`piAgentDirFor`, `host/src/integrations.ts:58-65`), and never `~/.pi/agent`.

### The kinds, and what each loads by default

- Four kinds can be chosen for. The main chat. Background: routines and the jobs hobkin delegates, which are the runs with no purpose. Work: its discover, look and do runs. Durable hobkins on Pi. A run's kind comes from its purpose, as `harnesses.mjs` reads it today.
- Each kind always loads these of hobkin's own, and starts with these of Pi's:

  | Kind | hobkin's own | Starts with, of Pi's |
  | --- | --- | --- |
  | Main chat | `prompt.md`, `taste.md`, `learning-context.md`, `v2-runtime.md`, `memory.md` and `canvas.md` (`src/cli/pi-session.mjs:121-133`); the persona, the user's directions, hobkin's memory and the decided items (`src/cli/hobkin-extension.mjs:27-34`); hobkin's tools | nothing |
  | Background | `background.md`. A routine also gets the user's directions and hobkin's memory, and its own memory and log (`src/cli/checks.mjs:79-87`) | `builtin:mcp`, pi-agentic-search, pi-search-hub |
  | Work | `background.md` and the run's `work-discover.md`, `work-look.md` or `work-do.md` (`src/cli/harnesses.mjs:57`, `:76`), with the user's directions and hobkin's memory | pi-agentic-search, pi-search-hub |
  | Durable hobkins | `durable.md` and `canvas.md` (`src/cli/hobkins.mjs:70-71`) | pi-agentic-search, pi-search-hub |

- The user, 2026-11-14: runs "will use their agents and the set of skills I want, which is almost my own development system. so team-leader, teams.md, how to use the default extensions". So the kinds do not start empty. `045-dev-system` ships the guides for these packages.
- The web search package is pi-search-hub, the one that gives `web_search` in the user's own Pi today: pi-web-access's own `web_search` is off in its setting there, so it adds only `fetch_content`, and pi-search-hub reads a page too, with `web_read`. hobkin's main chat loads no package today (`src/cli/pi-extensions.mjs:63-64`), so there is no main chat choice to follow. `045-dev-system`, "Guides for the extensions", has the details.
- The starting choice is written once, when the user turns the kinds switch on (below), and never again: an id the user turns off afterwards stays off. It names packages by their own names, `pi-agentic-search` and `pi-search-hub`, and picks the catalog id of the one installed, whatever its source: a folder on the user's Mac, or what `025-onboarding` installs on a new one. A package that is not installed is left out, and the Action Item says so.
- MCP stays where routines use it. 9 of the 25 routine files in the user's home read mail, a calendar or a home system through the MCP servers Integrations has on (read 2026-11-14), and many search the web. Background starts with `builtin:mcp` and pi-search-hub, so they keep working.
- The kinds switch. Until the user turns it on, Background, Work and durable runs load what they load today, through `namingExtensions` (`src/cli/harnesses.mjs:82-90`). It is off on every home until the user's go-ahead. Turning it on is the window's alone (`resources.start`, `outside`), from the "What agents load" tile, and it writes the starting choice and files one Action Item: for each kind, what it loaded before (every extension and skill Pi has on, Pi's AGENTS.md, and the MCP servers for the kinds that had them) and what it loads now, with a choice that opens Settings › Pi extensions. Turning it off puts runs back on what they loaded before and keeps the choice. `045-dev-system`'s texts, guard, plan command and helpers reach runs only while it is on.
- Every kind above also gets hobkin's own AGENTS.md and the skills `045-dev-system` lists for it. Background, Work and durable runs also get the project's own files of the folder they work in (see "Context files").
- The user's directions are `AGENTS.md` in hobkin's home, first copied from `agents-default.md` (`src/cli/directions.mjs:7-17`). ~~Settings calls them "hobkin's directions", so they are never taken for Pi's AGENTS.md.~~ Changed on 2026-11-14: Settings calls them "Your directions", since hobkin now ships an AGENTS.md of its own that Settings calls "hobkin's AGENTS.md" (`045-dev-system`). The project's files never bring them in a second time when a run works in hobkin's home.
- Always nothing of Pi's, and not choosable: hobkin's helpers (`owned_agent`) and its fixed runs: reflection, the humanizer, migration repair, session patterns and compatibility checks. Today a read or write helper still reads AGENTS.md, since only the theme helper gets `--no-context-files` (`src/cli/pi-extensions.mjs:82-84`). Every helper gets it now. Change Review's agent already loads nothing (`host/src/review/agent.ts:117-127`). A helper still gets hobkin's own texts, as `045-dev-system` decides.
- A run cannot reach a model that only an extension provides unless it loads that extension. Such a run fails before any prompt, as a run whose model Pi did not keep fails today (`src/cli/harnesses.mjs:291-294`).

### Where the choice is kept, and who changes it

- In hobkin's `config.json`, as `resourceSelection` version 2: for each kind, the chosen ids, at most 128, and whether the kinds switch is on and when the starting choice was written. `readResourceSelection` and `setResourceSelection` already keep it there, written atomically within the file's 64 KB bound (`src/cli/config.mjs:100-113`). Only tests ever wrote version 1, and one that is found reads as nothing chosen.
- Only the window changes it, on the user's click, through `resources.apply`, marked `outside` like the Integrations and Claude Code changes (`shared/commands/registry.ts:50-51`). hobkin may read it with `resources.read`. Its `client` tool refuses the change (`host/src/client-tool.ts:40`).
- Turning an id on checks it against the catalog and the kinds it is offered to. Turning one off always works, also for one that is gone.
- A chosen resource that is no longer installed stays chosen. The run starts without it, and the run's facts say it was missing. Settings marks it "No longer installed" with Remove. If it comes back under the same id, it loads again.
- A chosen extension that fails to load does not stop the run. Its error shows in the facts and in Settings. Today a missing or failing choice keeps the main chat from opening (`src/cli/resource-policy.mjs:47`, `src/cli/pi-extensions.mjs:53-55`). Now the chat opens without it. A required tool of hobkin's that is missing still refuses, as now.
- A change reaches Background, Work and durable hobkins at their next run or turn. The main chat takes it when its session next opens, after a restart or with a new conversation. Settings says so until then.

### How each run is held to it

- The main chat on its own child, which a live home uses (`host/src/owner.ts:429`): Pi's loader with every discovery off, as now (`src/cli/pi-extensions.mjs:63-71`), plus the chosen paths. Today nothing passes candidates, so nothing can be chosen (`src/cli/pi-session.mjs:73`). The runtime now builds them from the catalog. The chosen extensions' tools join the chat's tool list (`src/cli/pi-session.mjs:341`), and the check that refuses any other tool stays (`src/cli/pi-session.mjs:357-359`). A chosen skill also shows as `/skill:<name>` in the chat's slash list, which reads the chat's loader (`host/src/slash.ts:62`).
- The main chat behind a launcher: today it starts with all of Pi's defaults, since its arguments name no `--no-` flag (`src/cli/rpc-session.mjs:421-429`). It gets the same flags as the runs below.
- Background, Work and durable runs on Pi: today a run with tools names every extension Pi would load, and leaves skills and context files to Pi (`src/cli/harnesses.mjs:72`, `82-90`). Now each run gets `--no-extensions --no-skills --no-prompt-templates --no-themes --no-context-files --no-approve`, then `-e builtin:codemode -e builtin:tool-search`, `--extension` for each chosen extension path, `--skill` for each chosen skill path, and, after hobkin's own text, `--append-system-prompt` with the line that introduces the project's files and then each of them. These are Pi's own flags (`docs/cli.md` in Pi 1.5.0). An explicit `--skill` still loads under `--no-skills` (`docs/cli.md:202-203`), which is how hobkin's own skills reach a blank run. One runtime wrapper adds them, while the kinds switch is on. It takes the place of `namingExtensions` in hobkin (`src/cli/application.mjs:215`) and in the host's harness for a live home (`host/src/claude-code/agents.ts:23-26`), with a launcher or without.
- A launcher that manages its own extensions refuses `--no-extensions` (`src/cli/harnesses.mjs:66-67`). Under one, skills still follow the choice, Pi's AGENTS.md still stays out and the project's files still load, the extensions are the launcher's, and Settings says so.
- ~~Runs on Claude Code do not change. They load none of Pi's resources, and the user's own Claude Code setup loads, as `033-claude-code-agents` decided.~~ Replaced by the user's decisions of 2026-11-14: runs on Claude Code load none of Pi's resources, and no longer the user's own Claude Code setup either. They get hobkin's own texts and the project's own files instead. `045-dev-system` decides how. Settings says so for each kind the Claude Code tile sends there.
- This decides what loads. It is not a sandbox: a chosen extension runs its own code with the run's rights (`work-in-progress.md:388`, "not OS containment").

### What loaded, and what was used

- Chosen, loaded and used stay separate facts, as already decided (`work-in-progress.md:388`).
- Loaded is seen from inside Pi. hobkin adds one small extension of its own to every Pi run it starts. At each turn's `before_agent_start` it sends one status record under its own key, the way hobkin's bridge reports its tools (`src/cli/rpc-session.mjs:321-322`). The record holds the tools with the file each came from (`pi.getAllTools()` and its `sourceInfo`), the skills, and the context files Pi found by itself (`systemPromptOptions`), which should be none. A project's file counts as loaded when it was readable as the run began.
- Anything loaded that was not chosen and is not hobkin's or Pi's own is marked "loaded without being chosen", with the reason when hobkin knows it, such as a launcher that manages extensions.
- A use is a call of a chosen extension's tool, whether the model made it or a code mode script did (Pi gives nested calls their own `tool_execution_*` events), and a `read` of a chosen skill's SKILL.md. Context files and hobkin's own instructions are part of every turn they load in, so they have no uses.
- hobkin appends what loaded and what was used, by kind and run, to `resources/use.jsonl` in its home, kept to the last 30 days. For the main chat it writes a line when the session opens and after each turn that used something. Use stays on this Mac. It is no telemetry event and is never uploaded (`work-in-progress.md:463`, "no telemetry57 expansion").

### Commands

- `resources.read` returns the catalog, the selection, hobkin's own instructions for each kind, the last loaded facts of each kind, the uses of each resource by kind over 30 days, whether a launcher manages extensions, and which kinds run on Claude Code. hobkin may run it.
- `resources.apply { kind, on?, off? }` turns ids on or off for one kind and returns the same state. It is the window's alone (`outside`).
- `resources.start { on }` turns the kinds switch on or off. On the first time it is turned on it writes the starting choice and files the Action Item. It is the window's alone (`outside`). `resources.read` says whether the switch is on.

## Out of scope

- Choosing one extension or skill out of a package.
- A folder's own `.pi` resources and settings, and choices for one project, routine or Work item.
- MCP in the main chat. It has none today, and its loader refuses an MCP choice (`src/cli/pi-extensions.mjs:33`). Which MCP servers are on stays with `023-integrations`, and so does signing in to them from the app (the ledger's tasks 41 to 43).
- Choices for helpers and for hobkin's fixed runs.
- Pi's `SYSTEM.md` in Pi's folder, which would replace Pi's base prompt in runs that keep it. Pi has no flag to leave it out without replacing the prompt, and this Pi folder has none. `APPEND_SYSTEM.md` is already left out, since every run passes an append of its own (Pi's `dist/core/resource-loader.js:494-498`).
- Pi's own settings, such as compaction and retry. They are not resources.
- Passing Pi's resources to Claude Code runs.
- Installing, updating or removing Pi packages from the app. `pi install` stays in the terminal.
- ~~Editing or turning off hobkin's own instructions from Settings.~~ Changed on 2026-11-14: editing hobkin's AGENTS.md, its skills, Your directions and its runtime prompts is `045-dev-system`'s. Turning hobkin's own instructions off stays out.
- A switch for the project's own files. They load in Background, Work and durable runs whenever the folder has them.
- Loaded and used facts on the agent canvas or in a run's report.
