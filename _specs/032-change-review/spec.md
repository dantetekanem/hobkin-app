# Change review: levels, units and a story for every shipped change

## Outcome

When hobkin ships a change, the client reviews it in the background. It sorts the diff by metadata, maps every changed definition with four facts (what it does, whether a test proves it, who runs it, what undoes it), gives each unit a level (`safe`, `mid` or `high`) from a fixed table and one model pass, and writes the story a reviewer reads top to bottom. When the user opens the change, the story is ready: the Review screen opens on it, the Work card shows the level, and while a review is still running the client says what it is doing and how far along it is. pi-auto-review no longer reviews these changes.

## Decisions

- The design is `packages/change-review/skills/change-review/FOUNDATION.md`, written with Fable on 2026-11-12. Its rules are the rules here: four questions in order, the floor table of section 5.1, what a model may change (5.2), the buckets that are never read line by line (6), the units (7), the story (8), the blind check (9) and tracking (10).
- The engine lives in `packages/change-review` and stands alone. It imports only Node's modules and its own files, never `#shared`, `@/`, `hobkin` or anything else of this app, so it can be published by itself later. The host hands it a checkout, a range and a `ModelRunner`.
- pi-agentic-search, which is public, reports the search facts in `packages/change-review/notes/agentic-search-changes.md` and ships them there. It only searches. The engine reads its scan pack and still works, with weaker facts, on a pack without them.
- Proof is the repository's own tests, run where the change is checked out, with no clone and no sandbox. For a finished hobkin change that is a review worktree per project, owned by the client, kept between reviews and never the user's own folder. A test proves a definition when it passes at head and fails once that definition's changed lines go back to base, or, for a new definition, once its body is made to fail. No coverage tooling. Missing tests are a finding; the review never writes tests to fill the gap.
- ~~Levels: a change no test proves is `high`; the Reviewer may raise freely; the blind check may raise a level one step.~~ Replaced by the user on 2026-11-12: a level is the risk that the change breaks something, the code or what runs in production, and nothing else. That code changes what it does is what a change is, and is no reason for a level. That the tool could not check something is said in words and is never `high` on its own.
- Levels: first the floor table as a pure function of the four facts. `high` is a break that is shown (a dangling reference, a test that passes with the change undone and fails with it), an effect nothing undoes, or a changed contract nothing shows working. What no test showed, tests the tool could not run, and direct tests alone are `mid`, with a finding that says so. A change of behaviour that tests show through a request is `safe`. Then one model pass by the Reviewer, on the high tier with high thinking, which raises to `high` only by naming the input and the wrong result, lowers only with named evidence (5.2), marks critical, asks questions, says what to watch after launch, and writes the story's words. Then one blind check by Quick, on the fast tier, with an empty context and no tools. A review uses these two tiers and no other. The check changes no level: what it was not convinced by becomes a question for the reviewer. There is no second model loop.
- A test command that cannot start on this machine failed no test: the unit says its tests were not run, with the command's reason. A test that fails with the change in place is run once more with the definition put back, to learn whether the change is why.
- The model pass that narrated the graph walk is dropped. The graph keeps the host's own steps.
- A review writes `triage.json`, `graph.json`, `risk-events.jsonl`, `units.json`, `story.md`, `blind-check.json`, `progress.json` and `progress.jsonl` beside the review in the home. Every time in them is read from the clock.
- ~~The Review screen opens on the story. The node graph stays one key away.~~ Replaced by the user on 2026-11-12: the story is not a page or a tab. Reviewing happens in graph navigation: each step's explanation lives in its node, the sidebar keeps one stable description of the whole change with its overall risk badge, and Enter opens a split panel with the unit's explanation (with quick links to ask hobkin) beside its code.
- Navigation frames the node in focus at a reading size, never every connection it has; only the step's path stands out. A step pager sits at the bottom center. The request's life cycle (callers up to the entry point, the callees that matter) is drawn, with code the change did not touch dimmed.
- A verdict is confirmed in place: the button turns into "Click again to confirm" and goes back after ten seconds. A change that lands closes its review with a short celebration (five seconds at most).
- Discard is the no, the choice after every yes in the panel, in the color of what cannot be taken back and with no key of its own. On a pull request it closes it on GitHub without merging, through gh, as the user, with their words as a comment first when they wrote any. On a finished change it is hobkin's own no, the one its card gives, and its pull request is closed first when one is open. The branch stays either way. No review is posted, so comments written on it are not marked sent. The review leaves the list and is kept in the home with its notes, as a merged one is: Remove is what deletes a review. A discard the host refuses after the yes is shown to the user and never handed to hobkin's agent, whose shell could do it another way, unpinned. One verdict at a time goes on a review: the same yes from a second window joins the one under way, another is refused, and a pull request closed already is not discarded again.
- A pull request from GitHub is reviewed only after "Start AI review". A review being prepared says it can be closed and will be ready in the background, shows elapsed time, what it is doing and its steps, and hobkin says in the chat when it is ready. Work has an "AI Reviews" tab with every review, running or done.
- The Review page is reworked as the user described on 2026-11-12. The canvas has barely visible dots for depth. Nodes sit closer by default, at 1.2 times today's zoom. The panel is ordered: this step, then what matters for the reviewer, ~~then the agent they can ask (in a colour of its own, saying plainly what to type),~~ then the rest. Replaced by the user on 2026-11-12: the panel no longer imitates hobkin's chat. Comments and questions are written in one input at the bottom of the review (`009-review-notes`); a question goes to hobkin, whose own chat comes into view beside the review to answer while the keyboard stays in the review. The header says which project changes, the title and the lines changed, and an external pull request has a button for its description.
- On the Work card the level replaces the pi-auto-review grade, and "Get it reviewed" rebuilds this review instead of starting an agent run.
- Remove is on every row of the AI Reviews tab that is not running. It takes the review out of the list (`review.remove`) and nothing else: the change, its branch and its pull request stay, and the row says so while it asks. It is asked in place as a verdict is: the first click asks, a second within ten seconds removes, after ten it goes back, and a refusal from the host shows in the row.
- Each row also gives Discard and Discard and delete branch without opening the review: the same flow as the panel's (`createVerdictChoices`), so the host's preview shows in the row on the first click and the second does it. Review again and Stop stay as they are; Remove and the two discards sit together behind one small "More" on the row, opened in place. Each is a stop the keyboard walks, the first takes the keyboard when More opens, and Escape takes back the one waiting, then closes them (`ui/src/features/work/review-row-actions.ts`).
- Discard and delete branch (`discard-branch`) is the fifth verdict: everything Discard does, then the branch goes. It is the last choice in the panel and in the row, in the destructive color, with no key. On a pull request from GitHub its head branch is deleted on GitHub once the pull request is closed, only while it is still at the commit the preview showed: GitHub's `updateRefs` mutation moves `refs/heads/{ref}` from that commit (`beforeOid`) to nothing in one atomic step, so a commit pushed in between keeps the branch, and the preview says so. The REST delete has no such condition. It is deleted only when that branch lives in the repository the pull request merges into: a branch in a fork, in a repository that is gone, that repository's default branch, a protected branch, the branch of another open pull request, and a branch open pull requests merge into are refused in the preview, each with its reason, which points to Discard. The preview says the commits stay on the closed pull request, where GitHub can restore the branch. On a finished hobkin change, after its pull request is closed and hobkin took the no, hobkin deletes the change's own branch (its work action `deleteBranch`, `deleteItemBranch` in hobkin's `src/cli/work/controls.mjs`): the hobkin tree that goes with it first, then the branch on this Mac, then on origin, each pinned to the commit that was shown (`update-ref -d` with the old value, `push --force-with-lease`). That tree is the one holding the branch, or the item's own tree once it let go of the branch at one of its commits, and it goes only when nothing in it is uncommitted. hobkin refuses, before anything is done: while the item runs; when it has no branch; when the branch is not its own `hobkin/<id>-…` (never another's, never the default branch); when an item not yet finished works on it too; when the project's own folder, or any folder hobkin did not make, has it checked out; when its tree holds uncommitted work; and when the branch is gone already. The preview names the branch, where it is deleted (this Mac, GitHub or another origin by its address), the tree, the files git ignores in that tree, three by name and then how many more, and how many commits no other branch or tag on this Mac holds (a remote-tracking branch can name what origin no longer has, so it is not counted), or that such commits are lost when git cannot count them. Every untracked file in the tree counts as work never committed, also where the project's git config hides untracked files; hobkin's own trees and folder steps (keeping a finished run's work, holding a cut-short run's tree, taking or leaving the project's folder, retiring a tree) count them the same way. The token holds all of it, and hobkin deletes only when handed back exactly what it showed. A step that fails says what was already done and stops there; once the no went, the review leaves the list.
- In Change Review, Enter on a node opens its code, and Enter again closes it and puts the review back as it was: the wire the code closed comes back when nothing moved meanwhile, the lines picked in the code go with it, and a key pressed in the code that closes it gives the keyboard back to the review. After a move while the code is open, the reviewer stays where they went. Escape is unchanged.
- The model call is named "Review and reorganize the map" (the user, 2026-11-20: "careful pass should not be named that, that agent should also redefine, reorganize and regroup the nodes. adding or removing too"). The host's log calls the step "Reviewing and reorganizing the map". In the same one call the Reviewer may reshape the map the rules built, through a `map` list in its answer beside the events, words and claims: give a part a name and one line (`describe`), move a part to another unit (`move`), make a unit of parts taken from others, which is how a unit is split (`unit`), merge units (`merge`), order the parts of a unit or the units of the walk (`order`), add a part (`add`) and take one out (`remove`). Its events may name a part the list adds, and its unit words a unit the list makes. Code applies the list in order, checks each operation against the map as the earlier ones left it, and refuses one that breaks a rule below with a line in the review's problems. A refused operation changes nothing. An answer with no map, or an empty one, gives the review the rules alone give. The request stays one call; it also lists up to 40 unchanged definitions the scan found next to the change, and they are the first data cut when the prompt is over its size limit. For grouping this replaces FOUNDATION 11's "rules on structure": the rules group first, then the Reviewer reshapes within these rules.
- Reshaping sets no level and no fact. A part keeps the level its floor and the events give it, a unit is at the worst level of its parts, and a unit the Reviewer shaped is told by its first part at that level. A part that is always a unit of its own (critical, a broken reference, a schema change, a migration, a new condition check, a map entry that could not be checked) stays alone. A bucket's unit keeps what it holds, and a test is in no unit. Every unit is still built by curate, so it has the same fields in the same order; one the Reviewer filled with several parts has the grouping `regrouped` and lists each part with its own line.
- A part the Reviewer adds points at lines of a file of the change or of the scan, at head or, for removed code, at base: lines the file has, none inside a part already mapped, at most 200. On lines the change touched it is a part the map missed: no test was looked for, so its floor is `mid`, and its finding says the Reviewer added it. On unchanged lines at head it is context: a new row of the floor makes it `safe` because nothing in it changed. Unchanged lines at base are refused.
- A part the Reviewer takes out leaves the units and the story and stays in `graph.json` with its reason (`hidden`). Only a `safe` part comes out, and never one a test fails with or whose tests could not run, one that holds a condition check, carries a question, is named by a claim, sits in a bucket's unit or is always a unit of its own.
- On the Review page a node takes the Reviewer's name and line for the part it holds, when that part alone of its unit is on it. A context node of the graph that holds a part the Reviewer put in a unit is framed with that unit's step and says what the Reviewer said of it. A node whose parts the Reviewer took out says it left them out of the story, and why, and no step goes to it.
- The review is walked in one of two modes (the user, 2026-11-13: "a Free Roam mode, like Free Roam | Story"), chosen on a "Free Roam | Story" switch at the left of the pager's row, or with `O` and `P` anywhere in the review but a text field (`ui/src/features/review/story/mode.ts`). R and S, the first thought, are taken: R removes an open proposed wire and S hides the panel. O and P sit side by side, as the two do on the switch, and the switch shows them. Story is the review as it was. In Free Roam nothing leads: the pager is not shown, every arrow moves between nodes (Left and Right as Shift with them does in Story), a node a step tells is focused alone, the keys that walk the story move nothing, and no card offers to go back to a step. Enter, comments, questions and verdicts work as in Story. Choosing a mode, either way and the one on too, starts it from the beginning and closes the code: Story at its first step, framed as a step is; Free Roam with the whole graph in view and nothing in focus. The mode last chosen is remembered in the window (`reviewMode` in the review memory, under the same storage key), so the next review and the same one after a reload open in it; a saved state without it opens in Story.

- A change review takes hobkin's TLC runs at the reviewed head as evidence (the user, 2026-11-21: "if the TLA+ proof pass, why the agent saw as risk to deploy?" and "this must be taken into account for the review"). For a hobkin change the host reads, from hobkin's home, the run of each TLA+ model the change adds, edits or touches a file of, matched as work mode matches it (`modelFacts`: that commit, the spec as committed there, a broken run before one that held), and hands it to the engine as `modelChecks`. The Reviewer gets each one: the model, the result, the states, each rule and whether it held, and the actions that never fired. The engine stays free of hobkin. Levels keep their meaning: a model the diff adds or edits is `safe` by rule 2 when its check holds with every action run, and a break by rule 1 when a rule is violated. A file a model names in `\* models:` keeps the level its own rules give it, because a model is not a test of its lines; its reason says what the model shows and that a hold lowers no break found in it, and a violation is a finding on it. A risky answer names the models that hold.
- The panel lists each of the change's TLA+ models under "TLA+ model checks", above Needs a look, one row each: the file over what TLC said at the reviewed head with its states or the steps to the break, and Open run. A press opens the run on the proof screen (spec 050), and `T` opens the first run, whose row shows the key (the user, 2026-11-21: "i want the TLA+ proof to be accessed from the sidebar, easily, not hidden in here"). Rows keep their height while a check runs.
## Out of scope

- Pull requests from GitHub keep today's review: there is no local checkout to run their tests in.
- The parked skills in `packages/change-review/notes/parked`.
- Publishing a package, pushing a branch, or anything sent outside this machine.

## Acceptance

- A1. Triage puts every file of a diff in exactly one bucket, with the treatment FOUNDATION section 6 gives its kind: lockfiles and generated files are counted, pure renames are listed, locales are sampled, mass deletions are checked by reference, and code is scanned.
- A2. A locale missing a key, or a removal that something remaining still refers to, makes its unit `high` and critical. A complete locale batch, or a removal nothing refers to, is `safe`.
- A3. The floor of each of the twenty-two cases in FOUNDATION section 14 is the level and rule the table there gives.
- A4. A risk event can always raise a level. It lowers one only with a named evidence kind, never to `safe` when no test showed the change, and `critical` holds only on `high`. Applying the same events twice gives the same graph.
- A5. A test that passes at head and fails when a definition's changed lines go back to base proves that definition: `lifecycle` when it enters through an entry point, `isolated` otherwise, and `-observed` when the diff added or changed it. A test that still passes is no proof. A test that fails at head is a `high` finding.
- A6. Every node is in exactly one unit, also when the scan writes one call as two edges or two definitions call each other, a unit's level is the worst of its nodes, every unit has the same fields in the same order whatever its level, and more than nine units split into parts by entry point.
- A7. The story has an opening, a setting, the units (`high`, then `mid`, then `safe`) and a conclusion, and no level in it differs from `units.json`.
- A8. The blind check runs once, is saved unedited, changes no level, and leads to at most one action per unit.
- A9. While a review runs, `progress.json` names the current step and what it is doing, with status, measured seconds, done and total for every step.
- A10. A change hobkin finishes gets its review without the user asking, and the same commit is never reviewed twice.
- ~~A11. Opening a finished change shows its story first; the graph is one key away, and the Work card shows the change's level.~~ Retired 2026-11-12: the user replaced the story page with the story inside graph navigation. See A15.
- A12. Approve and Approve and merge in the Review panel do what they say, or say why they cannot.
- A13. The Review page shows the project, the title and the lines changed, keeps the panel in the order of the Decisions, and an external pull request's description opens from a button.
- A14. `agentic-search scan --diff <range>` finishes on a checkout whose working tree differs from the scanned head.
- A15. A finished change's review opens on its graph with a sidebar header that stays the same for the whole review and carries the overall risk badge; each step's explanation sits in its node; moving the focus frames that node at a reading size and never every node it is wired to; a pager at the bottom center counts and walks the steps; unchanged code on the life cycle is dimmed; Enter shows the unit's explanation beside its code; the Work card shows the change's level.
- A16. A verdict turns into "Click again to confirm" and goes back after ten seconds; only a second click sends it, for the commit on screen; a landed change closes its review with a celebration of five seconds at most.
- A17. A pull request opened from GitHub waits for "Start AI review"; while a review is prepared its page says it can be closed, shows the time, what it is doing and its steps, and keeps updating; hobkin says in the chat when it is ready; Work's AI Reviews tab lists every review, running or done.
- A18. Discard shows what it will do and does it only on the second click: a pull request is closed on GitHub without merging and leaves the lists, a finished change gets hobkin's no with its open pull request closed first, and a refusal from GitHub or hobkin says why and keeps the review.

- A20. - A21. Discard and delete branch is the last choice for both kinds, with no key. On a pull request it closes it, then deletes its head branch on GitHub, and refuses a fork, a repository that is gone and the default branch before anything is sent. On a finished change it closes the pull request, takes hobkin's no, then deletes the change's own branch, its tree and its copy on origin, exactly as the preview named them; hobkin refuses while the item runs, with no branch or another's, with an unfinished item on it, when the user's own folder or a folder hobkin did not make has it checked out, with uncommitted work in its tree, and when it is gone already. A verdict that would now delete anything else is refused, and a step that fails says what was done and stops.
- A22. In Change Review, Enter opens the code of the node in focus, and Enter again closes it and puts the review back as it was, with the keyboard in the review. Escape still closes it.
- A23. "Free Roam | Story" sits beside the pager with `O` and `P` on it; either, by click or key, starts its mode from the beginning and closes the code; in Free Roam every arrow moves between nodes, a step's node is focused alone and the step keys move nothing; the mode last chosen opens the next review and the same one after a reload, and a saved state without it opens in Story.
- A24. A changed line inside the callback of a top-level call, such as a service worker's fetch listener, is mapped as a change of that statement, so the review of such a change is built instead of stopping with "the scan produced no nodes".
- A25. A Discard or Discard and delete branch the host refuses after the yes shows the host's reason to the user and is never handed to hobkin's agent.
- A26. On a pull request, Discard and delete branch deletes the branch only while it is at the commit the preview showed, and refuses in the preview a protected branch, the branch of another open pull request and a branch open pull requests merge into; Discard alone still closes it.

- A29. Discard and delete branch on a finished change names the files git ignores in its tree, counts an untracked file as work never committed even where the project hides untracked files, and counts as lost every commit no other branch or tag on this Mac holds; hobkin's tree and folder steps see such untracked files too.
- A30. A definition a change deletes whole from a file that stays is a node of its own, read at its base lines, so a change that only takes code away is reviewed instead of stopping with "the scan produced no nodes"; the definition just before the deletion is not counted as changed by it.
- A31. A code change of only comments or blank lines, inside a function or outside any, is reviewed as safe with no unit and "Nothing that runs changed."; a change the review cannot map stops with its true reason, naming the files: those the search tool has no parser for, or lines that run changed with no definition found holding them, never a guessed wrong root.
- A32. The Reviewer's one answer may describe, move, make, merge and order units and parts, add parts and take them out. Each operation is checked against the map in order: one that breaks a rule is refused with a line in the problems and changes nothing. No operation changes a level, a criticality or a fact; a part always told on its own stays alone; a bucket's unit keeps its parts. An added part is refused off the change and the scan, past the end of its file or inside a mapped part, and is `mid` with no test looked for on changed lines and `safe` context on unchanged ones. A part above `safe`, one a test fails with or whose tests could not run, one that holds a condition check, carries a question or is named by a claim is never taken out; one taken out is in no unit and not in the story, and `graph.json` keeps it with its reason.
- A33. The model step reads "Review and reorganize the map" while a review is prepared, and no line a review shows says "careful pass". An answer with no map, or an empty one, gives the same units, story, words and problems as before reshaping existed.
- A34. On the Review page a node takes the Reviewer's name and line for its part, a context node the Reviewer put in a unit is in that unit's step, and a node whose parts it took out says so, with the reason, and is in no step.
- A35. A change review of a hobkin change is given hobkin's TLC run at its head of each model it adds, edits or touches a file of, and never says no checker result is shown when one is. A model the diff adds or edits is `safe` when its check holds with every action run and `high` and critical when a rule is violated; a file the model names keeps the level its own rules give it, with the model's result in its reasons; and a risky answer names the models that hold and says a hold lowers no break. A pull request, or runs that cannot be read, give the review none.
- A36. The review panel lists each of the change's TLA+ models with its file, its result and its states at the reviewed head, each row with a run opening it on the proof screen, and `T` opens the first. Each row keeps its height as a check runs and ends.

## Open questions

- In this repository most proof comes out `isolated` (tests call functions directly), so most units floor at `mid` by rule 6 and say what the direct tests leave unshown. A project could name its own life-cycle test paths and runbook in a config file at its root; that is not built yet.
- A repository gets one test command. A Rails app's JavaScript tests are not run, and a unit they cover says its tests were not run here. A second command per kind of test file is not built yet.

- A big monorepo's tests can be slow to boot. The budget in `reference/budget.md` assumes one to three minutes per test file. If proof runs long, it could run only for nodes whose floor is not already decided without it.
