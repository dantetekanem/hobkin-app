# hobkin's own development system

## Outcome

Every agent hobkin starts works from hobkin's own development system, not the user's. The user's global `~/.pi/agent/AGENTS.md`, their Pi skills and their Claude Code setup stay theirs, for their own terminal. hobkin's runs load hobkin's own AGENTS.md and its own skills: team-leader and teams for delegating with pi-extended-teams, as the user's own Pi does, a coding flow, an expert for each language, the humanizer, and short guides for the extensions a run loads. A run in a project also reads the project's AGENTS.md or CLAUDE.md, beneath hobkin's text. Before a Work run edits code, it reads hobkin's expert for each language it touches, reads the design, and records a plan on the item that hobkin checks. A change that mixes a refactor with a behaviour change, or passes 300 lines, is split. Before a run writes a commit, a PR's title or body, a review reply or a document, it has read the humanizer. Work runs are held to this order; Background and durable runs list the same texts and are held once the user says so. The user reads and edits each of these texts, and every other prompt hobkin ships, in Settings › Skills, puts any of them back to hobkin's version, or asks hobkin to change one. A text the user never edited follows hobkin's releases, and an edited one gets an offer when hobkin ships a newer version. hobkin's own review, Change Review, takes every place pi-auto-review had: the grade a card shows, the bar land offers and auto-merge use, and the reviews hobkin asks for by itself. All of this holds on Claude Code too.

### Short, and held by code where it can be

- From a talk the user shared (Lauren Tan, "All Code Is Slop (Except Mine)"): written rules stay short and say what an agent would not do by itself. When a correction comes back, a check (a lint rule, a test, a type) beats another rule line. Agents use comments to excuse a bad fix, so a comment says only the reason the code cannot show.
- "Evaluating AGENTS.md: Are Repository-Level Context Files Helpful for Coding Agents?" (https://arxiv.org/abs/2602.11988) found that context files did not generally raise task success, raised inference cost by over 20% on average, and helped mainly by naming non-standard practice.
- The user's own count points the same way. In the 30 days to 2026-11-13, Pi sessions read the language skill before their first edit in 43 to 71% of cases, and Claude Code subagents in 2 to 3%. The post-processing skills, which the global AGENTS.md names by language, were read more often (`~/Poetry/personal-pi/docs/coding-agent-skills/plan.md`, the baseline table).
- So hobkin's AGENTS.md stays under 500 words, and each other text under 1,500, except the humanizer, which stays whole as vendored, and swift, cut from 6,054 words to under 2,500. An adapted skill keeps what is not obvious and drops what a capable model does anyway.
- Where a rule matters, code holds it, and the text only says what code checks: the expert before an edit, the plan before an edit, the humanizer before a commit, a PR's text, a review reply or a document. See "The guard".

### The coding flow

- The user: "agent should know which language is working, get the design of the system, think and prepare what is going to change, and make the changes. it should know when to split into stack". The `coding` text says this, and loads in full in every Work do run:
  1. Name the languages the item touches, from its files and the manifest. Read hobkin's expert for each before the first edit.
  2. Read the design: `projectNotes` Architecture and Languages, the project's own AGENTS.md (already above), its `_specs/` when it has them, the nearest tests of each file to change, and two good files nearby that the change should look like. Agents copy whatever looks like the pattern, so pick those two on purpose.
  3. Plan before any edit, and pipe the plan to `work.commands.plan`.
  4. Proof first, as `work-do.md:37` says now. Then the change, with comments only for the reason the code cannot show.
  5. Run the project's own lint, type checks and tests, from `projectNotes` Test and Languages.
  6. When a correction keeps coming back, propose in the description a check that catches it (a lint rule, a test, a type), not another rule line.
- A plan holds the languages, the files, the change and the risk in a sentence each, the check that proves it, up to two example files, and the layers. This is where `layers` is defined, and `042-stacked-work` refers to it. As JSON:

  ```json
  {
    "languages": ["javascript"],
    "files": ["src/cli/work/store.mjs"],
    "change": "One sentence.",
    "risk": "One sentence.",
    "check": "The command or test that proves it.",
    "examples": ["src/cli/work/tree.mjs"],
    "layers": [
      { "title": "Move the reader into its own module", "kind": "refactor", "summary": "What it changes.", "proof": "How it is shown.", "estimate": 60 }
    ]
  }
  ```

  `kind` is `refactor`, `mechanical` or `behaviour`, spelled as hobkin's prompts spell it. `estimate` is the layer's changed lines. A layer has one kind, so a refactor and a change of behaviour are never one layer. `hobkin work plan` refuses a plan with a field missing, or with a layer over 300 lines that is not `mechanical` (a lockfile or generated code, which cannot be split), and says which. Today an item is checked only for a title and a brief (`work/store.mjs:494-500`).
- A plan belongs to the run that wrote it. The director makes a run's id in `start` (`work/director.mjs:888-890`) and builds the request after it, inside the run (`:918`), but a do run's commands come from `describeFor` (`:757-761`), which knows no run (`command`, `:495-497`). So `start` hands the id to the request, and `describeFor` puts it in the command: `work.commands.plan` is `hobkin work plan <slug> <item> --run <run id>`. The command keeps the plan on the item with that id, and refuses an id that is not a running do run of that item, read from the runtime's own record of runs, so one run cannot write another's plan. The run's wrapper gives the guard the same id, and the guard asks for a plan with it.
- The user: "if no experiment is done, Hobkin can know how to work with this and make the best plans". The sizes come from published practice. Google's review guide calls about 100 lines a reasonable change and puts a refactor in a change of its own (https://google.github.io/eng-practices/review/developer/small-cls.html). SmartBear's study of a Cisco team found reviewers should take in no more than 200 to 400 lines at a time (https://smartbear.com/learn/code-review/best-practices-for-peer-code-review/). The user's line is 300, which is also where hobkin already stops offering a branch to land (`work/patterns.mjs:12`, `:193`). So the coding text aims near 100, the plan check refuses a layer past 300, and no layer it allows is too big to be offered or reviewed.
- Lines are counted as land offers count them, additions plus deletions (`work/patterns.mjs:188`), so the plan and the offer agree.
- The coding text orders the layers: refactors and mechanical steps first, then the change of behaviour with its tests.
- The run does the first layer. Until `042-stacked-work` files the rest as layers of their own, they go in the description, as `work-do.md:38` says now for a larger item. How layers become stacked branches, and how they land, is `042-stacked-work`'s. This spec says when a plan splits and how it names the layers.
- When the run records `branch` or `pr`, hobkin counts the branch's changed lines and keeps them beside the first layer's estimate. The description names both. A later tuning of these numbers starts from that record.
- Every Work do run plans before its first edit, a `pr-fix` item included: `041-review-feedback` sends review feedback through this flow. A run that edits nothing, such as a clean rebase or a review round that finds nothing to fix, needs no plan. So recording `branch` or `pr` is refused only when the run made a commit and the item has no plan from it.

### The guard

- The user: "the post-processing idea was good but we need to drop, it should be instructions before addressing." hobkin ships no post-processing skill and no pass after the change. Most of each of today's three post-processing skills is guidance on how to write the code (naming, the shape of methods, honest types, what a test asserts), and that moves into the experts, read before the first edit. What is left, a look over the whole change, is the coding flow's last step: lint, types and tests.
- The user: "prose also must be a must, humanizer must always be used to write any text". Narrowed by the user on 2026-11-14 to "for writing PRs and documents": every commit message, PR title and body, review reply (`041-review-feedback`'s drafts) and document (a spec, a doc, a README, a report) is written with the humanizer read first. Chat replies are not.
- One pure module decides, and each harness asks it before a tool runs:
  - In a Work run, an edit or write of a file an expert covers waits, with the expert's path in the reason, until the run has read that expert. A file no expert covers never waits.
  - In a Work do run, any edit or write waits until the item has a plan from this run.
  - `git commit`, `gh pr create`, `gh pr edit`, `gh pr comment`, `gh pr review`, `gh issue create`, `gh issue comment`, a write of `work.item.prFile`, an outcome piped to `work.commands.item` that holds `replies`, and an edit or write of a document the manifest names wait until the run has read the humanizer.
- The guard holds Work runs. Background and durable runs list the experts and the humanizer and are not held until the user says so (the user, 2026-11-14): until then the run wrapper loads the guard only in Work runs, and holding the other kinds is a change to that one list. The main chat lists no expert and is not held.
- On Pi, a small extension of hobkin's does this at `tool_call`, which can block a call (`docs/extensions.md:364`; `owned-agent-extension.mjs:67-68` blocks this way today). A read counts when Pi's `read` tool, or a code mode script's nested `read`, opens the SKILL.md, the same as a use in 038.
- On Claude Code, a PreToolUse hook passed in the run's `--settings` asks the same module, and finds the run's reads in its transcript.
- It cannot see a file written through `bash`, such as `sed -i` or `cat >`. A run that made a commit without a plan still cannot record `branch` or `pr`, so the plan holds on every path.
- The main chat writes replies all day, so it does not load the whole humanizer on every turn. hobkin's AGENTS.md carries the core writing rules in a few lines, the humanizer is listed and read before the main chat writes a document, and the report editor still edits every report afterwards (`report-editor.mjs:41`). The user settled this on 2026-11-14: the humanizer is "for writing PRs and documents".
- The report editor and the main agent's brief write by the same humanizer text as the skill, the user's edit included (`humanizer.md:37-42`, `brief.mjs:27`). `humanizer.md` keeps only the editor's own part.
